# 失败创建的自动回滚设计（kind failed-create cleanup）

本文档说明 `pkg/cluster/internal/rollback` 的设计决策。代码只依赖 `Runtime`
抽象接口，真实 docker/podman provider 可在其 CLI 调用之上实现该接口；测试使用
完全内存化的 `fakeruntime`，可在指定步骤注入失败。

## 1. 问题与约束

创建一个三节点集群时，若第三个节点初始化超时，此前创建的容器、网络、卷以及
宿主机上的集群目录/临时凭证都可能已经存在。要求：

1. 只清理**本次创建**产生的资源；创建前已存在的同名集群绝不能被当作残留。
2. 宿主机已有同名集群时，重复创建必须尽早以“已存在”失败，回滚不得触碰其容器。
3. 回滚有总耗时上限，单个资源失败不能阻止其余资源清理，所有失败最终汇总。
4. 原始创建错误与回滚错误都必须保留，不能互相覆盖。
5. 保留现场（retain）时不执行回滚，但要列出遗留资源和手动清理办法。

## 2. 资源归属：意图台账 + 持久化状态 + 尝试标签 + 预检快照（四重机制）

两种朴素方案都有致命缺陷：

| 方案 | 风险 |
| --- | --- |
| 仅在创建时记录（进程内存） | 进程被 `SIGKILL`/断电，记录丢失，残留无法识别 |
| 仅靠资源标记事后识别 | 创建前已存在的同名资源可能被误认成本次残留而误删 |

本设计把两者结合，再加预检快照和磁盘状态，形成四重机制：

1. **意图台账（intent ledger，内存）**：每次创建生成随机 `AttemptID`。每个资源
   在**调用 runtime 创建之前**先登记 `intent`，创建成功后翻转为 `confirmed`。
   - 选择“先记录意图”而非“先创建再记录”：漏清理的代价（残留破坏下一次创建、
     需要人工介入）高于多尝试一次删除。台账中允许存在“有记录、资源不存在”的
     状态，因此回滚把 `not found` 一律视为成功。
2. **持久化状态文件（`creation-state.json`）**：台账在**任何 runtime 资源创建
   之前**先写入集群状态目录（目录本身也是被登记的本地资源），此后每完成一个
   步骤就原子刷新一次（写临时文件再 rename），内容含 AttemptID、预检快照基线
   和全部条目。这样：
   - 创建成功 → 删除状态文件，健康集群不会被误判为“未完成的创建”；
   - 回滚完全成功 → 删除状态文件；
   - 回滚有残留失败 → **保留**状态目录与状态文件，供二次恢复；
   - retain 模式 → 保留状态文件，作为手动清理的恢复线索。
3. **尝试级标签（runtime labels）**：本次创建的每个容器/网络/卷都带
   `io.x-k8s.kind.create-attempt=<AttemptID>` 与集群名标签。两个并发或重试的
   创建即使资源名相同，标签值也不同，永远不会混淆。
4. **预检快照（preflight snapshot，随状态文件持久化）**：创建开始前快照全部
   资源。回滚的每个删除都经过 `OwnedByThisAttempt` 闸门，必须同时满足：
   - 名称在台账中（intent/confirmed 均可）**或**资源带本次尝试标签；
   - 名称不在预检快照中（若同名资源被重新创建并带本次标签，则以标签为准）；
   - 当前快照里该资源若存在，必须带本次尝试标签。

   仅有 intent 而现存资源不带本尝试标签 → 判定为外来资源，拒绝删除。

### 两类极端情况的处理

- **进程被强制终止（SIGKILL、机器断电）**：内存台账随进程消失，但磁盘上的
  状态文件和 runtime 标签都在。下次运行通过 `RecoverOrphans` 加载状态文件，
  拿到**原始 AttemptID 与预检基线**，再按标签扫描 runtime 重建台账，随后正常
  回滚。只按标签认领、绝不按名称认领，因此创建前已有的同名资源不受影响。
  残余风险有两个窗口：① 资源已创建但 runtime 还没写完标签的极短窗口内被杀；
  ② 状态文件首次落盘前（首个本地目录创建之前）被杀。两者都只能靠后续
  `kind delete cluster` 按集群名标签人工兜底，命令行提示与本文档均说明该限制。
- **同名资源创建前已存在**：预检快照 + 标签双重否决，回滚不会删除；网络这类
  共享资源若已存在则直接复用、不登记归属、失败后也不删除。

## 3. “已存在”的尽早失败

`Creator.Create` 在任何写操作之前先做一次快照，发现带本集群名标签的容器即返回
包装了 `ErrAlreadyExists` 的错误（与现有 provider 的
`node(s) already exist for a cluster with the name ...` 行为一致）。此时台账
尚未建立，没有任何资源被创建，因此**不触发回滚、没有任何 mutating 调用**，
已有集群的容器、网络、卷原样保留。测试 `TestDuplicateNameFailsEarly` 断言
runtime 调用记录中不存在任何 create/remove/stop。

## 4. 归属记录的提交时机

各类资源运行时登记时机不同，统一采用“intent → 创建 → confirmed”两段式：

| 资源 | 顺序 | 说明 |
| --- | --- | --- |
| 状态文件 | 一切之前 | 先建状态目录并落盘空台账，之后每步原子刷新 |
| 本地路径（集群目录、临时凭证） | 最先 | intent 后写文件/建目录，再 confirmed |
| 网络 | 先于容器 | 已存在则跳过且不归属 |
| 命名卷 | 容器之前 | intent 后创建 |
| 容器 | 按节点顺序 | 创建返回的**匿名卷**通过 `CreateResult.Created` 补登 |
| 节点初始化（kubeadm init/join） | 全部容器之后 | 第三个节点超时即发生在此阶段 |

容器创建可能在 runtime 侧隐式生成匿名卷（docker 的匿名 `--volume`），
`CreateContainer` 把这些附属资源一并返回并 `MarkConfirmed`，避免泄漏。

回滚对“找不到”的容错规则：

- **可忽略（视为成功）**：`ErrNotFound`（含 intent 从未物化的资源）、本地路径
  `os.IsNotExist`。
- **可重试（有上限）**：`ErrInUse`（容器尚未断开导致网络/卷删不掉）、daemon
  瞬时不可用等其它错误，指数退避重试至 `MaxAttempts` 或总超时。
- **必须上报**：重试预算耗尽或 context 到期后仍失败的错误，进入聚合错误，
  同时出现在最终的 leftovers 清单中。

## 5. 清理顺序与依赖关系

`Rollbacker.Rollback` 严格按依赖顺序执行：

1. **限时导出节点日志**（独立 deadline，失败仅告警，见 §6）；
2. 所有归属容器先 **stop**，再按创建逆序 **remove**；
3. 刷新快照后，按逆序删除归属卷（匿名卷、命名卷）；
4. 删除归属网络；
5. 删除本地内容：先文件、后目录（`RemoveAll`）。集群状态目录特殊处理：回滚
   全部成功时正常删除；只要前面有任何失败，就保留目录与 `creation-state.json`，
   为二次恢复留线索。

容器逆序删除保证依赖方先消失；网络/卷删除安排在容器删除并刷新快照之后，规避
“删除调用已成功但资源仍在删除中、网络因容器未断开而失败”的竞态。仍出现
`ErrInUse` 时由有界重试吸收（`TestTransientNetworkDeleteRetried`）。

单个资源失败只记录、不中断；最终 `Aggregate` 汇总全部失败，并再做一次快照生成
leftovers 清单。`CreateError` 同时保存 `CreateErr` 与 `RollbackErr`，实现标准
`Unwrap() []error` 契约，`errors.Is` 可到达两类原因中的任意一个，谁也不能
覆盖谁。

## 6. 失败现场保留与日志导出

- **默认（自动回滚）**：回滚开始前在 `LogsBaseDir`（默认临时目录）下建
  `kind-failed-logs-*` 目录，通过 `LogExporter` 钩子限时
  （`LogExportTimeout`，默认 10s）导出各节点容器日志，成功则把目录路径放进
  返回错误并打印。导出失败或超时：删除半成品目录、告警、**不阻止回滚**。
  钩子化是刻意的：真实 provider 可直接接入现有 `kind export logs`
  （`CollectLogs`/`logs.DumpDir`），无需把完整集成塞进本包。
- **显式保留（Retain=true）**：完全不执行回滚，不发任何 stop/remove 调用；
  返回的 `CreateError` 带 `Retained` 标志、完整 leftovers 清单，以及逐资源的
  手动清理命令（`docker rm -f` / `docker volume rm` / `docker network rm` /
  `rm -rf`）。

## 7. 中断信号与强制终止

`signals.go` 的 watcher 语义：

- **第一次信号**（SIGINT/SIGTERM）：取消创建 context，当前步骤 unwind；回滚使用
  **独立的、带总超时的新 context**（`context.Background()` + `Timeout`），因此
  信号本身不会让清理失去执行机会，同时 `Timeout`（默认 30s）保证终端不会被
  长时间卡住。
- **回滚期间再次收到信号**：调用 `SignalPolicy.OnSecondSignal`（生产接线为
  `os.Exit(130)`，测试注入钩子避免杀掉测试进程），立即退出。
- **SIGKILL/断电无法防御**：这是持久化状态文件 + 标签 + 下次运行
  `RecoverOrphans` 的覆盖范围；状态文件落盘前与标签写入中的残余窗口见 §2。

## 8. 与现有行为的差异

| 维度 | 现有行为 | 本设计 |
| --- | --- | --- |
| Provision 失败 | 直接调 `delete.Cluster`，按集群名 `ListNodes` 后 `docker rm -f -v` | 台账+标签+预检三重归属判定，只删本次资源 |
| 动作阶段失败 | 同样按名删除，删除错误被 `_ =` 丢弃 | 有界重试、聚合上报，创建错误与回滚错误并存 |
| 网络 | 共享 `kind` 网络，从不删除 | 保持共享语义：预检已存在则复用且不归属；本次自建网络才回滚 |
| 卷 | 依赖 `rm -v` 顺带删匿名卷 | 匿名卷显式登记并验证删除，命名卷单独管理 |
| 本地内容 | kubeconfig 移除分散在 delete 路径 | 集群目录、临时凭证纳入同一份资源清单；持久化台账跨进程可恢复 |
| 失败现场 | 仅 `--retain` 保留，无清单 | retain 输出 leftovers 与手动命令；默认回滚前限时导出日志 |
| 信号 | 无专门处理 | 首信号触发受控回滚，二次信号强制退出 |
| 耗时 | 无上限 | 回滚总超时 + 单资源重试次数双重上限 |

## 9. 测试覆盖（内存假运行时）

`fakeruntime` 模拟容器/网络/卷与匿名卷、容器-网络附着关系，并支持按步骤注入
失败与记录全部调用顺序。场景：

1. 第一个节点初始化失败；
2. 第三个节点初始化失败（题述主场景）；
3. 网络创建失败（含 intent 无资源的容错、本地路径回滚）；
4. 回滚时某容器删除永久失败（其余资源照常清理、错误聚合、原始错误保留）；
5. 重复创建同名集群（最早失败、零 mutating 调用、已有容器存活）；
6. retain 保留现场（无删除调用、清单与手动命令齐全）；

外加：网络 `ErrInUse` 瞬态重试、重试预算耗尽、回滚硬超时、成功路径无回滚、
日志导出先于删容器、导出失败不阻塞、进程被杀后的持久化台账恢复
（`TestOrphanAdoptionAfterLostLedger`、`TestStateFileLifecycle`、
`TestLoadLedgerMissingFile`）、无标签同名资源拒绝认领、预存在网络复用不删、
context 取消仍回滚、intent 无物化资源容错、容器创建中途失败、聚合错误哨兵
可达性。每个场景都断言：删除调用满足 stop→remove container→remove
volume/network 的依赖顺序，且预置的外来集群（容器、共享网络、卷）在所有场景中
零改动。所有测试通过 `-race` 运行，全部用例无真实等待（Sleep 可注入），
整套包测试秒级完成。
